# WB-3 实施决策与边界

2026-11-08，依据 WB-1 已确认 D01–D03、WB-2 设计与结果线程，以及用户全权推进 MVP 的授权。下列默认由本次实施选择，区别于用户逐条确认。核算版本为 `interval-v1`；修改算法需新增版本与明确迁移，不能重刷已审核历史。

## 已确认规则的落实

| 规则 | 本实现 |
| --- | --- |
| D01 首次派工冻结 | 工单首次派工在同一事务锁内冻结该产品当时全部工序版本、产品量换算后的工序计划量；随后各工序派工引用该快照。版本包含价、标准、单件数量、名称/顺序和开关。档案调价、改标准不影响旧单。 |
| D02 协作分量 | 原始参与区间扣除暂停及有原因的审核前时间修正，得到有效参与时间；按其比例分配本批合格与不良量。保留原始、有效、最终核算工时。数量4位，内部权重使用未舍入精确比例。 |
| D03 增量分批 | 每次报工关闭并归属尚未报过的有效区间，继续状态则同刻重开。各批数量与区间唯一归属，不重复。最终按钮在同一时刻登记末批并完工；普通分批不会完工。 |
| 并行核算 | 按员工切分全部区间边界；独占片全归本工序，重叠片按冻结单位标准 × 本批个人精确工序量加权；每片分配整数微秒，保持员工总投入守恒。 |

## 采用的 MVP 默认

- 数量为整数万分之一工序单位；单件数量同精度。产品量×单件数量只换算一次，计划量按四位四舍五入。单价以**分/工序单位**录入（保留2位元）；标准为整数微秒/工序单位（输入秒可6位）。金额按批次合格量×冻结单价，先四舍五入到分，再按有效时间比例分配分值，不良不计薪。
- 时间权重默认使用**本批合格＋不良的总工序量**，表示全部实际生产投入；计件仍只按合格量。此项与 WB-2 推荐“不良不自动入权重”不同，属于本次授权内的明确默认，修改须发布新核算版本。数量、时间、金额用 `math/big` 精确乘除；展示分钟的浮点格式化不进入计薪/核算路径。
- 尾差按最大余数分配，余数相同以持久化员工ID/批次ID排序。ID在原记录生命周期固定，因此重算确定；不因当前组长变化转移尾差。
- 协作和并行分别保留工序开关，但首版**协作任务排他参与**，即使两个开关同时开启也不与其他任务并行。对每名成员检查；暂停保留占用，恢复时再次检查。组长统一开工/暂停/继续/报工/完工，变员和移交均留事件；离场前须先移交给在场成员。
- 工序派工累计预占不能超过冻结计划量。超派工报工保留原数，审核卡显示提醒，由主管明确点击审核处理。暂不加前后工序流转门槛。工单关闭不终止在制任务。
- 并行批次以区间交叠形成依赖闭包；关联任务数量未齐时待核算，数量齐备后整组联合通过，避免分批审批锁死依赖。只修正未审核数量时保留原批次、原计时窗和追加修订，不额外产生数量。已审核批次拒绝改量、改时或驳回；后续工资调整须独立设计审批，不覆盖历史。
- 审核前允许主管追加“扣除异常时间”区间，有原因/操作者/时间；原始参与不改，重叠扣除取并集。扣除区间必须落在该员工本批原始有效区间。全部扣除导致无有效参与则待核算，不能审核；缺失时间的补录作为后续。
- 零标准保留原始时间并待处理。主管可在审核页明确提供人工异常标准与核实原因，按关联批次追加 `resolutions`，原冻结标准仍保留0，结果标注人工异常核算；正常非零冻结标准不能通过该入口替换。这是受审计的例外处理，不是自动取最新档案补算。
- 普通员工只能看本人任务和个人统计；主管/管理员可维护、派工、审核与审计。MVP 不建立复杂的跨车间权限矩阵，管理员/主管生产操作可用于演示或现场代办，操作人记录真实会话；未强制禁止自派自审。生产应按岗位使用主管与员工独立会话。
- 会话随机令牌存 PostgreSQL，Cookie 使用 HttpOnly、SameSite=Strict，HTTPS下可选 Secure；写操作校验 CSRF，登录也有预会话校验。终端空闲15秒由客户端清屏退出，服务端独立核验；操作会刷新闲置时限。身份退出从不改生产计时。后台密码运行时读取并 bcrypt 校验，未连接真实硬件，不把工牌码当高强度安全凭据。
- 工单导入为 UTF-8 CSV（支持 BOM），显式本地编码映射，external_id 幂等；整批事务，错误整批回滚。文件缺失行不自动关单，文件明确 closed 才关。已冻结后产品、车间或数量改变拦截，避免暗改计划；真实 ERP 适配入口为 `OrderSource.ReadOrders`，当前实现 `CSVSource`，没有假造现场字段。
- 日期按上海时区报工日归属，可按月/起止日期筛选；当前是月度生产汇总，尚不是工资月结。班次、夜班开班日、锁月/补发、辅助作业、返工与 ERP 入库对账留待后续。

## 必须知道的核算限制

整批数量作为每片权重会对报工切点敏感（WB-2 C13）：A/B 同时做60分钟，标准均1、总量各20；双方整小时各报20得30/30分钟；A半小时各报10、B整小时报20，则每半小时是10:20，得20/40分钟。当前选择此清楚、可复现的首版口径；建议并行任务共同检查点报量。将来若采集分段产量或改为按批内时间估算片段产量，必须明确升级规则，不能静默重算已审核数据。

首版所有写入由 PostgreSQL 事务级 advisory lock 串行化，状态在关系表中保存，sqlc显式列投影读取/写入，约束保证外键和唯一性；不依赖单进程互斥。一次读取全量业务数据，区间对比为二次扫描，适合小规模车间演示。历史增长后需改为按工单/员工/月份查询及分区锁，不把当前吞吐当生产规模承诺。

## 可追溯性与重放

`versions` / `snapshots` / `revisions` / `trims` / `resolutions` / `audits` 均追加写，业务入口不会更新旧内容；`batches.good/bad` 保存原输入，修正只读最新修订。`spans` 保存服务端微秒时刻及批次归属，`allocations` 保存个人量、原始/有效/核算时间与分值。审核结果禁止业务入口修改，新报工不会重算它；数据库管理员的直接SQL操作不在应用授权范围内。审计事件含操作者、服务器时间、对象和输入原因，主数据旧值可通过历次事件及工序版本追溯。

每个页面写操作带请求标识；成功回执和业务写入在同一事务保存。同键同参数返回原结果，同键异参数拒绝；并发同一请求只写一次。原始/修正/分配/审核关系不依靠审计 JSON 维系，核心实体有真实 PostgreSQL 外键。

数据库迁移和种子可重复运行；种子仅用于空演示库，不会覆盖现有资料。无外网CDN依赖；提供容器和 Ubuntu systemd 模板，未部署公网、未合并主线、未连接现场ERP。
