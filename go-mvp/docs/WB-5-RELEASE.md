版本：`WB5-interval-v2-r1`，2026-11-08。增量基于 PR #6 的 `84da8eb`；PR #6 尚未合并，当前增量 PR 以 `agent/mika/02be5388edb5` 为基准。原 Python 系统未修改，真实易飞 ERP 与物理刷卡硬件尚未接入。

## 核算规则与可追溯依据

新增报工显式保存 `batches.algorithm = interval-v2`，分配行也保存版本。迁移仅增加该列；旧行默认 `interval-v1`，待审和已审均不自动升级。所有旧已审分配行在重算时直接保留。

协作数量仍采用 D02：个人精确工序量 = 本批总工序量 × 个人有效参与时间 / 全体有效参与时间。合格、不良分别按此比例分配，金额仍按本批合格量 × 冻结单价计算到分。原始时间、扣除修正后的有效参与时间、并行后的个人最终投入分别保留。

v2 对每个员工按有效区间边界切片，在片内将其本批个人精确工序量按有效参与时长投影：

```
片段估算个人工序量 = 本批个人精确工序量 × 片段时长 / 本批该人有效参与时长
片段权重 = 冻结单位标准 × 片段估算个人工序量
个人本工序最终投入 = 各片按权重分得的实际时间之和
```

片段时长为该片各任务共同因子，实现中直接比较“标准 × 个人精确量 / 个人有效时长”，等价且避免额外舍入。使用 `big.Int/Rat`，不使用展示时已舍入的四位个人数量。**这是假设本批有效时间内产量均匀的估算，没有采集真实片段产量**；批内速度显著变化、变员后生产效率变化时，估算不会声称还原真实产量，应按实际检查点报量。暂停、离场和审核前扣除区间不进入有效时长。

A/B 同时60分钟、相同标准、各20工序单位：双方整批、A拆2批、A拆4批，均30/30分钟；v1在A拆2批时为20/40分钟，回归已复现。完整重叠的标准120/60秒、数量10/40基准保持20/40分钟。等长部分重叠保持40/50；暂停案例按新时长密度得到约17.142857/42.857143。每片整数微秒用最大余数分配，总实际时间守恒；切片不同可能产生微秒级尾差，每片每项小于1微秒，不承诺超出测量精度的逐行完全相同。数量万分之一单位及金额分值也用稳定ID处理尾差，按批计薪的分值舍入口径保持不变。

## 旧待审与异常处理

- 旧待审批次继续用 v1，原始数量、时间、价格快照不变。主管可在“核算版本处理”选择目标版本，填写核实依据及原因；一次统一整个关联依赖闭包的未审批次。审计事件记录每个批次的原版本、目标版本、操作者、时间和原因，同请求重复提交只产生一次变更。
- 同一关联组中版本不同，整组显示“版本依赖”并阻止审核。若没有已审依赖，可明确统一为v2；存在已审依赖时只能沿用其版本，已审结果不可改，关联数量/时间依据也锁定。不存在自动混算或自动取最新工艺版本。
- 缺少重叠任务数量时列出工单、工序及派工ID，提供“去补报”链接；数量齐全后自动完成同版本核算。驳回批次须按原因修正重报。
- 冻结标准为0时不自动取新档案；主管在零标准入口追加核实后的正标准和原因，保留原冻结0值及异常记录。权重合计为0、全部有效时间被扣除或缺少明细时不允许审核，展示具体原因；完全无有效时间须先核实原始区间和修正记录，不允许编造投入时间强行通过。缺失时间补录与已审工资更正仍为后续范围。

## 并行与协作组合

两个开关都开启的协作工序可以与其他允许并行的任务共同运行。对每个在场成员检查其全部进行中或暂停任务，任一排他任务都拦截。整队开工/恢复先完成所有成员校验，再写区间，避免部分开工；暂停保留占用，暂停加入也检查冲突。加入/离场、恢复、组长移交和报工闭环沿用同一套规则和审计。离场前须移交给在场成员。协作分量依赖有效参与时间，最终投入依赖并行权重，二者没有循环依赖。新工序默认两个开关仍关闭、单件数量仍为1。

## 页面可见改进

终端运行/暂停使用不同卡顶色和状态标识，显示允许并行/排他、单人/多人、待报工时间。派工、累计已报、审核通过和剩余可报分别展示，清楚标注累计含待审/驳回和剩余不小于0。报工输入明确“本次新增”。任务按进行中、暂停、待开工、完工排序，并可按员工、工单/工序/组长关键字与状态查找。

报工审核支持员工、工单/批次关键字和状态筛选，区分待报工依赖、待核算、待审核。核算卡显示算法与估算假设、具体阻断原因、关联批次和补报入口。统计和CSV也区分待核算，CSV带算法版本。

业务提交使用同一原生表单和JSON回执：失败在表单内反馈并保留输入，处理中禁用重复点击；成功回到对应任务/批次并显示具体结果。同URL连续成功强制刷新，确保每次使用新的幂等标识。无脚本时仍可正常提交。公共终端保留大按钮、登录扫码焦点、换人退出、15秒闲置清身份；提交处理中维持会话，收到回执后重新计15秒，浏览器恢复缓存时清除旧身份页面。

## 实测与升级方法

隔离 PostgreSQL 15 实例端口55433，浏览器候选实例18080；业务冒烟未向现有55432数据库写入任何测试工单、种子或计时。Go单元与真实数据库测试覆盖完整/部分重叠、不同切批、暂停、协作变员/移交、每个成员冲突、量/钱尾差、旧版重放、跨版本原因与幂等升级、原已审不可变、迁移重复执行、权限及15秒过期。执行 `go test ./...`、`go vet ./...`、`go test -race ./...`，以及前端构建。

Playwright原有11项闭环和WB-5新增8项检查通过，包括失败输入保留、17秒延迟回执期间不退出、具体补报入口、跨版本统一后可审核、390px终端无横向溢出。截图来自隔离演示数据。真实现场备份恢复到另一隔离库，连续迁移两次后全部原业务字段一致，3条已审批次及其结果未重算。私有备份不在源码包及公开附件中。

本机已有的 launchd 测试环境采用以下入口升级（Ubuntu/systemd部署继续沿用原模板）：

```sh
cd go-mvp
npm ci && npm run build
go build -trimpath -ldflags '-X workshop/internal/app.BuildVersion=WB5-interval-v2-r1' -o bin/workshop .
python3 scripts/upgrade-local.py upgrade bin/workshop
```

脚本只针对现有 `com.multica.gongshi-jijian-go-mvp.app` 作业，先核对其准确PID/命令及Multica daemon PID。保留数据库、旧二进制、配置及源码的私有副本，停止应用后制作一致备份，执行兼容迁移并逐字段检查，然后原子替换应用、恢复监督和验证健康；不停止PostgreSQL、不seed。启动失败在未写入v2业务事实时立即恢复旧应用，迁移新增列可留存，无需恢复覆盖数据库。

版本、二进制SHA256、备份名称和核验结果保存在持久目录的 `run/version.json`。健康页响应头 `X-Workshop-Version` 可确认运行版本。服务由原有launchd作业持续托管，监听 `http://127.0.0.1:8080`；日志在持久目录的 `logs/`。原 `service.py status` 查看状态，`service.py stop` 会同时停止应用与数据库，仅在需要停止整个测试环境时使用；再次启动用 `service.py start`。

如升级后尚未产生v2报工，可在源码中执行：

```sh
python3 scripts/upgrade-local.py rollback <本次升级返回的备份目录名>
```

回退只换回旧应用/源码，保留全部数据库记录。若已出现v2报工，该入口会明确拒绝旧算法回退并保持当前服务，应使用兼容v2的修复版本；不得用备份覆盖升级后新增业务。此限制保护新记录的版本含义。
