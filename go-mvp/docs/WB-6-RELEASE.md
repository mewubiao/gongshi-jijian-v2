# WB-6 完整流程效率优化

版本 `WB6-flow-efficiency-r1`。增量基于 PR #7 的 `408b66a`；本轮 PR 应以 `agent/mika/b6cb7ea868ed` 为 base，需先处理 PR #7 的依赖。本轮不合并 PR、不发布公网。

## 走查后优先处理的四个问题

1. 连续报工成功后重新加载整页，打断输入焦点，还会丢失当前筛选。
2. 给多人分别派工要反复选择同一个工单、工序，容易与多人共同完成一单的数量混淆。
3. 登录、任务详情和统计都读取全部关系表；统计页没有数据库分页。
4. 每次保存把未变化的历史资料、审计及核算结果逐行重新写入，SQL往返随历史增长。

## 已实现

- 员工开工、暂停、恢复、报工及完工成功后，以服务端当前任务卡替换原卡。连续新增量报工仅一次POST，更新累计/已审/剩余数量、生成新幂等标识并选中合格量输入框；失败保留原输入并通过 `aria-invalid` / `aria-describedby` 定位字段。不会把上一批数量自动当作下一批新增量。
- 手机端身份导航压缩，任务筛选按需展开，当前任务进入首屏；末批完工和继续报工使用完整大按钮。计时由服务器的累计值、时间锚点和浏览器单调时钟驱动，不产生秒级请求；自动换片不续身份。实际输入及提交中的保活仍有效，15秒闲置退出和换人清身份继续生效。
- “多人各自派工”一次选工单工序，按人填量，显示合计、冻结计划及剩余可派量；员工支持姓名/编码查找，所选员工保留显示。员工区域滚动，合计与保存按钮不会被长名单推到页尾。各人分别生成一张任务。原“单人派工 / 多人协作一单”仍使用一张任务、一个共同数量。
- 批量派工在同一事务、同一锁中，逐人复用原派工校验、工单冻结、数量上限、权限和审计；任一项失败整批不写入，也不留下半份冻结快照。同一请求重试不重复派工；并发超余额只允许一整批成功。
- 审核增加车间筛选，成功操作保留工单、员工、车间及状态筛选。既有缺数量、零标准、版本依赖的原因和直达处理入口沿用；本轮批量流程选择派工，未新增批量审核。
- 员工卡号识别使用已有唯一索引；终端只读相关任务及所需区间、快照、修正，不读取全库审计、请求及核算分配。
- 统计在SQL中筛选、稳定排序 `(at,batch_id,allocation_id)` 和每页50条；总数、已审汇总、员工合计来自同一查询快照与同一筛选。CSV按完整筛选导出，即便URL带 `page=2` 也不截成当前页。上海时间月份、起止日期和员工可见范围保持一致。
- 保存比较事务开始时的行内容，只向数据库写变化及新增行。仍执行原核算、权限、幂等和审计；原先全局写锁保留。迁移只增加读取索引，无业务字段重写。

## 同环境实测

独立 PostgreSQL 15、端口55434，两个二进制共用同一数据库：基线 `408b66a`（18081）与候选版（18080）。构造40员工、100工单、400派工、4000历史批次及各4000区间/分配/审计/请求，另含浏览器场景数据。正式采样开始时实际共46员工、115工单、427派工、4035批次、4037分配行。响应大小与原始数据在交付的 `clean-measurements.json`。无其他数据库测试或浏览器操作与这一组采样并行。

每个读取先预热，再顺序采样25次；连续报工先预热，再采样5次。SQL数量从独立PostgreSQL的 `log_statement=all` 日志计数，包含事务和会话查询。响应为本机HTTP端到端，不能据此推断生产吞吐或并发容量。

| 场景 | 中位数，前→后 | p95，前→后 | SQL/次，前→后 | 业务HTTP请求，前→后 |
| --- | --- | --- | --- | --- |
| 全范围统计列表 | 203.360→25.231ms | 204.783→25.647ms | 2→3 | 1→1 |
| 单员工统计 | 167.485→8.034ms | 168.668→8.244ms | 2→3 | 1→1 |
| 指定任务读取 | 168.127→1.653ms | 170.181→1.974ms | 2→2 | 1→1 |
| 员工连续新增量报工 | 2050.761→338.969ms | 2054.182→339.877ms | 21558–21578→14 | 2→1 |

统计SQL增加一次筛选目录读取，但避免了整个业务库的投影、解码及前端全量渲染；全范围统计响应由1,220,783降至33,550字节。统计汇总仍覆盖所有筛选数据。写入SQL的基线数量随新增历史行略增；优化后只写本次变化。

真实浏览器为两名员工各派20/30工序单位：表单操作10→7次，重复工单/工序选择4→2次，提交2→1次，业务请求 `POST+GET` 共4→2次。计数不含登录、准备数据、可选搜索及截图；见 `steps.json`。连续报工截图是同一任务、相同数据在两个版本的页面。

## 本地更新与回退

沿用 `scripts/upgrade-local.py`。只停止确切的launchd应用PID，并与Multica daemon PID核对；保留数据库服务和所有生产区间。停机后制作私有数据库备份，保存旧二进制、源码和版本哈希，兼容迁移、逐字段比较、原子替换、恢复服务并确认健康；不seed，不从备份覆盖新增业务。

```sh
go build -trimpath -ldflags '-X workshop/internal/app.BuildVersion=WB6-flow-efficiency-r1' -o bin/workshop .
python3 scripts/upgrade-local.py upgrade bin/workshop
python3 scripts/upgrade-local.py rollback <本次返回的备份名>
```

回退会核对备份二进制与版本元数据的SHA256：已证明支持v2的旧WB-5版本可保留新增v2记录直接回退应用；无可信兼容证明的旧版本继续受原有双重数据库检查保护，出现v2记录便拒绝回退。保留停机前最后一笔报工的并发保护；升级失败优先恢复可用应用，始终不恢复覆盖数据库。运维单元测试的目录显式隔离，`WORKSHOP_LOCAL_ROOT` 可指定独立测试状态目录。

访问地址仍为 `http://127.0.0.1:8080`，由原launchd持续托管，版本可从 `/healthz` 的 `X-Workshop-Version` 确认。持久状态在 `~/.local/share/gongshi-jijian-go-mvp/`；日志 `logs/`，备份 `backups/`，版本记录 `run/version.json`。`python3 ~/.local/share/gongshi-jijian-go-mvp/service.py status` 查看状态；`stop` 停止整个测试环境、`start` 恢复。

## 当前边界

首次冻结、协作有效参与分量、分批新增量、并行实际工时守恒和已审历史不变。写操作仍全量载入领域状态、串行核算；主管概览/审核/资料仍采用原读取路径，因此未声称整站所有操作都变为常数开销。当前实测支持先保留这一简单事务模型，未新增缓存、队列或框架。真实易飞ERP、物理刷卡硬件、缺失时间补录和已审工资调整仍属既有后续范围。
