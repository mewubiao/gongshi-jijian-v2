# 多角色代码检查与优化

日期：2026-11-07。基于当前报工 MVP，检查管理端、终端、角色范围、领域服务、工价留痕、月结辅助工时和 ERP 对账代码，并使用五类演示角色走查浏览器流程。本轮不新增数据库迁移，不重算历史记录，不改计薪公式。

## 角色检查与已完成改进

| 使用者 | 发现的问题 | 已完成处理 |
| --- | --- | --- |
| 班组长 | 翻页或只输入查询条件后，“待审核”默认条件可能丢失 | 默认条件与查询参数分别处理，翻页、搜索仍保持待审核；主动选择全部状态仍有效 |
| 班组长 | 每处理一条报工都要退出详情、重新找原列表 | 增加“通过／驳回并返回列表”，保留工单、月份、状态及页码；返回地址仅允许对应业务列表 |
| 班组长 | 工作台只显示总量，难以判断待办 | 显示负责班组范围内的待审核数量，增加新建派工、报工及辅助审核快捷入口 |
| 班组长 | 单人派工仍显示整组名单，容易误选后报错 | 表单随单人／整组切换显示，单人不提交隐藏的组员；无 JavaScript 时仍有原服务端校验 |
| 工人 | 任务列表被截断，已完成记录挤占待做任务 | 默认显示待处理、运行任务优先；可按工单、产品、工序搜索及切换全部，每页 20 条，无总数截断 |
| 工人 | 完工、暂停、辅助工时填写失败后输入清空 | 保留数量、原因、说明、类别和开工人员选择，减少重复输入；提交说明必填的类别增加前端提示 |
| 工人 | 已重报的驳回历史仍显示重复重报按钮 | 显示新报工链接，历史不再提供重复提交入口；服务端保留防重复校验 |
| 工人 | 手机上表格文字被压成竖排，详情难点 | 报工和辅助工时记录在小屏幕显示为卡片，放大详情操作区域，支持筛选 |
| 工人 | 辅助工时只显示最近 20 条，修正和驳回结果不清楚 | 分页访问全部本人记录，显示当前有效分钟、原始值及驳回原因；报工也显示修正说明 |
| 管理员 | 二维码工牌只显示前 100 人，不能定位员工 | 姓名、工号、班组搜索及每页 24 人打印，取消总数截断；同页预载班组，避免逐人查询 |
| 管理员 | 员工关联账号、班组的下拉框随人员增多变慢 | 使用 Django 现有自动完成控件，沿用普通账号与技术超级用户保护规则 |
| 工艺人员 | 旧页面可能覆盖其他人刚修改的工价 | 签名工价版本校验，后台事务中锁定当前工序，失效页面提示刷新；模型保存和旧新值历史读取共用事务行锁 |
| 工艺人员 | 进入维护路径长，产品选择和检索不方便 | 工序／产品快捷入口、产品自动完成，工序可搜编码和产品名称；历史去掉无权限员工链接，按本地时区显示 |
| 财务／工人 | 页面名称暗示可以审核，默认只显示待审 | 查询角色默认全部状态，显示查询文案；审核和反审核权限仍由服务端角色及班组范围校验 |
| 财务 | 列表只看到原始数量、原始分钟，需逐条点开核对修正 | 列表显示当前有效值，并保留原始值提示；零修正也正确显示，不覆盖原始字段 |

## 查询效率

- 普通账号的一次权限检查由两次员工读取减少为一次，不跨请求缓存角色，角色修改仍即时生效。
- ERP 对账将逐工序、逐报工查询修正改成数据库分组汇总。回归场景中，11 道工序从 14 次查询降至 3 次；数量口径保持原规则。
- 月结已审核辅助工时按员工在数据库内汇总，避免逐条查修正。
- 终端首页只查询当前状态，不再读取每个任务的全部会话和历史报工；分页限制单页渲染量。
- 二维码工牌预载班组、工价历史预载操作人和产品，消除对应的逐行关联查询。

## 产品经理已确认并落实的两项业务边界

2026-11-07 已收到确认：

1. **有进行中的生产任务或辅助作业时禁止月结锁账。** 已在共用锁账方法、持有月结期间行锁后检查。暂停与整组同样视为未完工，错误提示列出部分任务／员工／辅助类别，须先完工并完成审核。新开工使用冻结归属日，历史无快照记录沿用既有班次归属算法，不补写历史。其他月份的任务不误拦当前月份。
2. **派工保持负责班组内所有启用员工。** 不按角色收紧为工人／班组长，不改变历史派工和终端识别权限。新增回归覆盖五类角色继续可以被派工。

本次新增 7 项回归，该阶段全量测试为 183 项通过；主要实现为 `settlement/checks.py`、`SettlementPeriod.lock`，对应测试位于 `settlement/test_running_work.py` 与 `dispatch/test_workflow.py`。不新增迁移。
