# 派工与审核页面

管理端登录后，可从工作台或顶部导航进入业务页面。页面沿用已经确认的角色和班组范围，列表、详情、候选项和提交操作均在服务端校验。

## 派工

- `/dispatch/`：按工单、工序或员工查询派工记录，每页 20 条。
- `/dispatch/new/`：班组长选择负责班组所在工作中心的未结工单，只显示启用产品、启用工作中心且剩余量大于零的工单。
- `/dispatch/new/<工单ID>/`：填写单人或整组派工、工序、数量、人员、计划日期和备注。
- `/dispatch/<派工ID>/`：查看任务、派工名单及相关报工。

单人派工选择执行人；整组派工选择小组长和其他组员。小组长列在派工名单第一位，保留为整组尾差接收人；其他组员按班组编码、员工编码排列。小组长移交不改变第一位。全部人员都须属于当前班组长负责的启用班组，且员工启用；多人可来自同一班组长负责的不同班组，任务仍归第一位组员所在班组。

每次提交都按数据库当前的工单状态和剩余量校验，不信任旧页面或旧对象。工单已关闭、工序不属于产品或已停用、人员越出授权范围、单次派工数量超过剩余量时拒绝创建。继续沿用已有规则：单次与易飞剩余量比较，不把同一工单所有派工量加总，也不扣减易飞剩余量。

`Dispatch.submission_key` 为页面提交的唯一标识。同一表单重复提交返回已创建的派工，不重复创建名单。数据库用唯一约束兜底；历史派工的该字段保持空，不补写或改动历史数量。新打开一张表单会产生新标识，因此仍可有意创建另一条派工。

## 报工审核

- `/reports/`：按状态、归属月、工单或报工人查询；班组长默认待审核，查询角色默认全部状态。列表显示当前有效数量，修正时同时提示原始数量。
- `/reports/<报工ID>/`：显示原始数量、当前有效数量、原始打卡工时、当前有效工时、冻结单价、冻结标准工时及审核留痕。

班组长可对负责班组的待审核报工执行：

1. 直接通过：修正项留空，沿用当前有效值。
2. 修正并通过：填写数量或小时／分钟／秒，并填写修正原因。填写任一工时项即表示修正整段工时，未填部分按零处理。零是有效修正值，不等于留空。
3. 驳回：在独立驳回表单填写原因，保留原始报工，由原报工人按既有流程修改后重新提交。

有效完工数量超过派工数量时，页面提示并要求勾选核对确认。即使原始数量没有超量、在本次审核中把数量调高到超量，也必须确认。

从列表进入详情会携带筛选条件和页码，返回列表时保留。批量逐条处理可使用“通过并返回列表”或“驳回并返回列表”，每次仍单独核对当前记录并提交，继续执行签名版本、权限、超量和锁账校验。

系统管理员可在未锁账月份对已审核报工反审核，须在页面确认，操作人和被撤销的审核信息继续留痕。系统管理员不替代班组长做普通审核。

## 辅助工时审核

- `/auxiliary/`：按状态、归属月、员工或作业类别查询；班组长默认待审核，查询角色默认全部状态，列表显示当前有效分钟。
- `/auxiliary/<记录ID>/`：查看原始和当前有效分钟，审核、修正并通过或驳回。

修正分钟必须填写原因，可修正为零，最多四位小数。原始有效分钟保留。仍按既有月结规则，只汇总通过审核的分钟，不计算金额。员工可在 `/terminal/auxiliary/` 登记、提交和撤回；辅助工时重报和反审核入口尚未提供。

## 事务与权限

- 所有写操作使用 POST 和 CSRF 校验，操作人取当前登录员工，忽略客户端指定的派工人、审核人。
- 财务、人资和工人按已有角色范围查询，不能调用审核操作；工人报工仍只开放本人本月和上月。
- 审核页面带签名版本，状态、修正、驳回、最近审核或反审核有变化时，旧页面提交被拒绝，须刷新后核对。重复审核不会重复追加修正记录。
- 审核按“月结期间 → 业务记录”的顺序请求锁，与月结锁账共用期间行；修正和最终审核结果在同一事务提交，失败一并回滚。没有月结期间时创建开放期间作为锁定对象。
- 业务页面写入使用 `dispatch.services`、`reporting.review`、`timekeeping.review`，后续入口也应复用这些流程。

## 当前边界

新单人报工已在提交时冻结并行等分工时。详情同时保留原始打卡值，当前有效工时优先使用审核修正，其次使用冻结分摊值；历史记录保持原值并在重叠时提示人工核对。终端操作和分摊算法见 `TERMINAL.md`，已审核报工的月结金额计算见 `SETTLEMENT.md`。

本地 SQLite 不支持数据库行级锁。重复提交约束、旧页面拦截、事务回滚和锁账拦截已有测试；生产数据库上的真实并发尚未验证。
